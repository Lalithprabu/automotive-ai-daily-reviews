# Sourcing disclosure -- Day 22: S2Planner

This project's standing rule: never fabricate a paper's results, and always disclose exactly what came from the source vs. what is this project's own reconstruction default.

## Paper

**S2Planner: Multi-Scale Semantic Planner for End-to-End Autonomous Driving**
arXiv:2609.29813, submitted 2026-09-24. Zhaowei Lu, Liguo Zhou, Yujie Guo, Lei Yu, Alois Knoll. Technical University of Munich; Huaibei Normal University.

## Access attempt

`arxiv.org/abs/2609.29813` was fetched successfully once (recovering title, authors, affiliations, submission date, and abstract), but a follow-up fetch to `arxiv.org/html/2609.29813` for the full text was rejected by this session's web-fetch proxy with an HTTP 429 rate-limit and an explicit "do not retry" instruction -- the same recurring wall this project has hit on most days since Day 9. `alphaxiv.org`'s mirror was used for a second pass and recovered abstract-level architectural description but not the full paper (no dimensions, loss functions, ablations, or full results table were recoverable). No GitHub repository or public code release was found for this paper as of this run.

## What is paper-sourced (verbatim or directly attributable)

- Title, full author list, both institutional affiliations, submission date (2026-09-24).
- Input: three front-facing cameras + ego-motion history + current driving command.
- A fine-tuned DINOv3 visual backbone paired with a "Spatial Tuning Adapter," producing multi-scale image representations.
- A coarse-to-fine decoder using trajectory self-attention and camera-projected cross-attention.
- Ego-conditioned trajectory initialization combined with iterative, geometry-guided sampling of multi-scale image features, described by the authors as the paper's central contribution.
- One headline number: **88.03 PDMS** on NAVSIM v1 navtest -- **with the authors' own caveat, quoted directly**, that this run was selected using navtest performance itself, so the number is exploratory and should not be read as an unbiased estimate of generalization. This project repeats that caveat every time the number is mentioned rather than presenting it as a clean benchmark result.

## What is this project's own reconstruction (not paper-sourced)

Everything else in `s2planner/` is a disclosed default:

- **The backbone.** DINOv3 is a multi-billion-parameter self-supervised vision foundation model this project cannot download or fine-tune inside a scheduled cloud session. `SyntheticBackboneStem` in `src/model.py` is a small 2-layer CNN stand-in -- it is explicitly NOT DINOv3 and makes no claim to reproduce its features. It exists only to give the Spatial Tuning Adapter and the cross-attention mechanism *some* multi-channel feature grid to operate on.
- **The dataset.** The paper trains on real front-camera driving video (implicitly NAVSIM-derived, given the evaluation benchmark). This project generates fully synthetic scenes instead: a parametric curved-lane corridor with lane-boundary and obstacle-vehicle landmarks in 3D ego coordinates, splatted into per-camera feature grids via an actual pinhole projection (`src/geometry.py`) -- so the camera <-> BEV geometric relationship the cross-attention exploits is genuine, even though the "camera images" are synthetic feature splats rather than photorealistic renders.
- **Camera rig intrinsics** (60px focal length equivalent, 1.4m mount height, ±32° yaw for the left/right cameras, 64×64 feature-grid resolution): this project's own default, tuned only so that lane and obstacle landmarks are visible within the synthetic image bounds at typical scene distances (5-40m). Not the paper's actual camera geometry.
- **The Spatial Tuning Adapter's exact form** (a bottleneck: 1x1 conv down to 8 channels, GELU, 1x1 conv back up to 32 channels, scaled residual, one adapter instance per pyramid scale): a standard, generic adapter-tuning recipe, not the paper's specific design.
- **The ego-conditioned initializer's parameterization** (an MLP over flattened ego history + command one-hot, predicting a per-step (speed, curvature) profile that is then differentiably integrated via a unicycle model): this project's own choice for what "geometry-aware initialization" should mean mechanically. The paper does not specify its initializer's internal form at the level of detail recovered here.
- **The camera-projected cross-attention's exact formulation** (per trajectory point: project current (x,y) into all 3 cameras, bilinearly sample that stage's feature pyramid level at the valid projections, then a learned query/key/value softmax attention over the up to 3 camera observations, with a learned "unobserved" fallback embedding for points invisible to every camera): implements the paper's named mechanism (camera-projected cross-attention, iterative/geometry-guided sampling) as literally as this project could manage from the abstract-level description, but the specific attention formulation, the "unobserved" fallback, and the number of decoder layers (3, one per pyramid scale) are this project's own design.
- **The loss** (coarse-to-fine supervision: every refinement stage supervised against the same ground truth with linearly increasing weight from the coarse init to the final stage): a standard, generic coarse-to-fine training recipe, not paper-sourced.
- **All reported synthetic-data numbers** (val ADE/FDE, the 59.8% ADE reduction from cross-attention refinement) are this project's own measurements on its own synthetic dataset and are **not comparable** to the paper's 88.03 PDMS NAVSIM number -- different metric, different benchmark, different data distribution, much smaller model (59,849 parameters vs. a DINOv3-based model that is almost certainly in the tens-to-hundreds-of-millions-of-parameters range).

## Why S2Planner was selected (Day 22 selection notes)

Re-ran the standing four-category sweep (ADAS vision perception, multi-modal trajectory forecasting, EV battery, V2X) for the 2026-09-12 to 2026-09-26 window. Direct arXiv listing pagination remains unreliable for this session (repeated `skip=` requests to `arxiv.org/list/...` return the same early-month page), so the `pastweek` listing endpoint was used instead for cs.RO and cs.CV, plus targeted keyword searches.

Candidates found and set aside:
- **Dense Coverage, Sparse Refinement: Byte-Constrained Cooperative Perception** (arXiv:2609.29456, ~2026-09-24) -- still the freshest V2X candidate as of this run (unchanged from when Day 21 flagged it), set aside again as this series' would-be 4th V2X entry (Days 12, 13, 19), and because its core contribution is bandwidth allocation rather than a prediction architecture.
- **Joint RUL + Capacity Estimation** (arXiv:2609.21932) -- battery category, but Day 18 (ChargeIC-LSTM) already covered the battery category recently within this window.
- **"Combining Evasive and Braking Reactions for Safety Reference Models in Automated Vehicles"** (arXiv:2609.29738) -- a classical control/safety-reference-model paper, not a learned prediction architecture; weak fit for this project's PyTorch-core-model requirement.
- No fresher pure-BEV-perception or trajectory-forecasting-specific paper was found in this window beyond ground already covered (Sparse-BEVNet, Day 14; EKF-neural fusion, Day 16; MM-Future, Day 15).

**S2Planner** (arXiv:2609.29813, submitted 2026-09-24, 2 days old at run time) was selected: the freshest genuine architectural-novelty fit for the "prediction problems" framing (end-to-end trajectory planning is a prediction problem), and -- unlike every prior end-to-end-driving entry in this series (SV-WAM's world-action model, MM-Future's joint world-action generation, READ/DRiF/RiskWorld's risk fields, ForeDrive's JEPA-style latent world model) -- it is the first entry to plan a trajectory directly from a modern vision **foundation model** backbone (DINOv3) via geometry-guided cross-attention, with no world model or risk field in the loop at all. That is a genuinely distinct mechanism from every world-model/risk-field entry so far, and its named components (Spatial Tuning Adapter, camera-projected cross-attention, ego-conditioned geometry-guided initialization) gave a concrete, well-specified basis for an honest from-scratch reconstruction.

## Implementation notes (bugs found and fixed)

One real bug, caught by visual inspection of the rendered simulation rather than by a passing/failing test (the tests were all correctly checking numerical behavior, not visual coverage): the initial camera-rig intrinsics (60px-equivalent replaced an even narrower first guess of 260px-equivalent focal length at 64x64 resolution) put most ground-plane landmarks outside the image bounds for the center camera specifically -- a scene's center-camera panel rendered fully black even though the BEV panel and telemetry were both correct, because the vertical field of view implied by a 260px focal length at 1.4m mount height was too narrow to keep near-field ground points (5-15m ahead) inside a 64px-tall frame. Fixed by reducing the focal length to 60px-equivalent (a much wider, more dashcam-realistic field of view) and retraining from scratch on the corrected geometry -- both the dataset's camera-feature splatting and the model's own cross-attention sampling read the same rig via `make_camera_rig()`'s shared default, so the fix is applied consistently to training and inference alike. Retraining after the fix produced a *better* result (59.8% ADE reduction from cross-attention refinement vs. 49.3% before the fix), consistent with the corrected geometry giving the cross-attention mechanism more useful in-frame camera content to sample from. Worth carrying forward: a synthetic camera-projection dataset's default intrinsics deserve an explicit "what fraction of landmarks land in-bounds per camera" sanity check before training, the same way this project already checks for degenerate/near-zero training signal in other ways (Day 13, 14, 18's lessons) -- a numerically "working" pipeline can still be visually broken in a way no loss curve reveals.

A second, more minor finding while writing `simulate.py`: Pillow's `save_all` GIF writer automatically merges pixel-identical consecutive frames into a single longer-duration frame (this is normal GIF-encoding behavior, not a Pillow quirk introduced by this project). The rendered simulation was built from 42 individually-drawn frames, three of which per scene are an intentional "hold" on the final refined trajectory; Pillow reports the resulting file as 24 frames with a correspondingly longer duration on the held frames, and the total playback duration (18,900ms) matches the original 42-frame plan exactly -- confirmed directly, not assumed, before treating the lower frame count as expected rather than a rendering bug.
