# Sourcing & Disclosure — Day 21: ChronoFuse

**Paper:** "Bend the Clock: Predicting Ahead to Beat Latency in Event-Based Object Detection"
**arXiv:** [2609.26919](https://arxiv.org/abs/2609.26919) (submitted 2026-09-22)
**Authors:** Biswadeep Sen, Benoit R. Cottereau, Nicolas Cuperlier, Terence Sim, + 2 additional authors (full roster not recoverable — see below)
**Affiliations:** National University of Singapore (NUS), CNRS, Université de Toulouse, CY Cergy Paris Université, ENSEA

## What was actually recovered from the paper

`arxiv.org/abs/2609.26919` and `arxiv.org/html/2609.26919` both returned HTTP 429
(rate-limited) on every attempt this session — the same recurring wall this
project's log has hit on most days since Day 9. A third-party mirror
(alphaxiv.org) recovered:

- The full title, a 4-name partial author list (+2 more, names not shown by the mirror), and affiliations.
- The verbatim problem framing: event-camera detectors take tens of milliseconds to run, so by the time a detection is available the scene has already changed; ChronoFuse instead predicts object state **for the time the output becomes available**, not for the time the input was observed.
- The mechanism name and one-sentence description: "causal cross-time fusion over a multi-scale feature hierarchy, combining current representations with cached temporal features," without requiring future data.
- Three evaluation datasets by name: **1 Mpx** (automotive driving data), **FRED** (rapid drone motion), **EV-Flying** (extreme drone motion).
- Four headline numbers: **71%** of latency-induced accuracy recovered on driving data; **9.3×** sAP gain on EV-Flying (20.95 vs. 2.25 sAP for the strongest standard event detector); **0.17M** added parameters; **0.84ms** added latency.

**Everything else — the exact internal wiring of ChronoFuse (the finite-difference velocity term, the causal temporal-attention cache summary, the latency-gated residual fusion), the backbone architecture, the detection head design, dataset splits, training schedule, and the full results/ablation tables — was NOT recoverable and is this project's own reconstruction**, built to be consistent with the paper's abstract-level description and its ~0.17M-parameter budget for the fusion module, not a reproduction of the paper's real implementation.

## Why this paper was selected (Day 21 selection notes)

Re-ran the full four-category sweep (ADAS vision perception, multi-modal trajectory forecasting, EV battery degradation/thermal, V2X latency) for the 2026-09-11 to 2026-09-25 window. Strong same-window candidates considered and set aside:

- **Dense Coverage, Sparse Refinement: Byte-Constrained Cooperative Perception** (arXiv:2609.29456, submitted 2026-09-24, 1 day old) — a genuinely fresh V2X bandwidth-allocation paper (task-aware benefit selector ranking BEV cells for a two-tier dense-coarse/sparse-refined transmission budget, 0.60 vs 0.52 mAP@0.5 on DAIR-V2X at 1.87KB vs 4.61KB/agent). Set aside because it would have been this series' **4th** V2X entry (Days 12, 13, 19) and its core contribution is a resource-allocation/selection mechanism rather than a temporal *prediction* mechanism — a weaker fit for the scheduled prompt's "prediction problems" framing than ChronoFuse.
- **Joint Remaining Useful Life Prediction and Capacity Estimation of Lithium-Ion Batteries Using Partial-Charging Data** (arXiv:2609.21932) — EV battery, but Day 18 (ChargeIC-LSTM) covered the battery category only 3 days prior in this window; not the freshest or most differentiated pick available.
- **Safety-oriented pedestrian trajectory prediction at urban intersections using time-to-collision and crossing-zone context** — submission date confirmed as 2026-08-31, outside the 14-day window; excluded on freshness.
- A January-2026-dated V2X collision-prediction paper surfaced by an initial search (arXiv:2601.17216) was checked and excluded — its arXiv ID month prefix correctly reflects a January submission, nearly 8 months outside the window; a reminder (per Day 13's earlier lesson about a mis-dated racing paper) that a paper surfacing in a "recent" search doesn't guarantee a recent submission date.

**ChronoFuse (2609.26919)** was selected: freshest genuine fit for the "prediction problems" theme (it is *literally* a predict-ahead-to-beat-latency mechanism), opens a new sub-category for this series (event-camera-based ADAS perception with latency compensation — distinct from every BEV/frame-camera detector covered on Days 3, 14, and others), has a clean old-vs-new story (stale detect-then-report vs. predict-for-availability-time), concrete paper-reported headline numbers, and — unusually well — its own natural "old way / new way" ablation is expressible as a single trained model with a component toggled on/off, which made for an honest, single-checkpoint simulation rather than needing two separately-trained models.

## Implementation notes — one real bug, caught and fixed

The first full training run converged smoothly (loss 2.81 → 0.33) but produced **worse-than-random** held-out center-distance error (~57-79px against a 9px "just copy the last position" heuristic) — a result "wrong" enough (per this project's standing rule that a suspiciously extreme metric is a stronger bug signal than "needs more training," established Days 13/14/16/17/18) that it triggered a dedicated overfit-a-tiny-batch diagnostic before touching hyperparameters.

**Root cause:** `build_targets` gaussian-splats a smooth heatmap peak around each object's *continuous* (sub-pixel) center, but `focal_loss` identified "positive" pixels via `target_heatmap.eq(1.0)` — exact equality to 1.0. Since object centers are almost never exactly integer-aligned to the stride-4 grid, the gaussian's peak value at any single discrete pixel is almost always slightly less than 1.0, so the positive mask matched **zero pixels** on nearly every training step. The heatmap loss silently collapsed to ~1e-8 while predicted probabilities stayed pinned near zero everywhere — a "trains cleanly, learns nothing" failure that a loss curve alone does not reveal.

**Fix:** after the gaussian splat, explicitly force the exact discretized center pixel to `1.0` (the standard CenterNet convention) — see the inline comment in `src/utils/losses.py::build_targets`. Confirmed on the same tiny fixed batch: center-distance error dropped from 44.7px (before fix, still improving despite the bug because size/offset losses were still live) to 0.08px after 300 overfit steps.

A second, non-bug design fix was needed once the loss was correct: the initial training loop only ever supervised the `enable_chronofuse=True` path, so the shared detection head had never seen the feature distribution produced when ChronoFuse is disabled — evaluating the "old way" ablation at that point measured a distribution-mismatch artifact, not the old way's real accuracy. Fixed by training both paths jointly each step (ChronoFuse-enabled supervised against the *future* position, ChronoFuse-disabled supervised against the *current/stale* position — see `train.py::run_epoch`'s docstring), which produced the sane, honest comparison reported below.

## Verified results (this repo's reconstruction, synthetic data, CPU)

- `pytest tests/ -v` → **16/16 passed**.
- `train.py --config config.yaml` (12 epochs, 640 train / 128 val synthetic scenes, CPU, ~4m 59s) → train loss 3.51 → 0.53.
- Held-out validation center-distance error (pixels, synthetic — **not** the paper's sAP):
  - Stale / no-compensation heuristic (copy last observed position): **9.36px**
  - Same weights, ChronoFuse disabled (learned "detect current position" head, evaluated against the future ground truth): **9.58px** — essentially matches the naive heuristic, as expected: a detector with no temporal-compensation mechanism has no way to know where the object will be by the time its output is used.
  - ChronoFuse enabled: **5.60px** — a genuine **40.2%** reduction in error versus the stale baseline.
- `simulate.py --config config.yaml --checkpoint checkpoints/chronofuse.pt` → `chronofuse_simulation.gif` rendered (24 frames, 1100×500px, ~1.46MB) from the real trained checkpoint, confirmed valid via Pillow re-open; visually reviewed — the "old way" (orange) box visibly lags the "ground truth" (aqua) box in high-latency scenes while the ChronoFuse (blue) box tracks it closely.

This repo's 40.2% synthetic recovery figure is a more modest number than the paper's reported 71% — consistent with this project's established pattern (a small-scale synthetic reconstruction on a CPU training budget underperforming a paper's real result on real data), reported honestly rather than tuned to match.
